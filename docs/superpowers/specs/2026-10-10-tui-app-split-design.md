# TUI 应用脚本拆分设计

日期：2026-10-10

状态：待审阅。拆分路线已确认；本文件定义设计，具体实现步骤另写 implementation plan。

## 1. 背景与目标

`src/tui/app.py` 当前约 2,700 行，同时包含应用入口、约 310 行样式、自定义控件、配置表单、项目管理、详情展示、错误报告处理、Zotero 操作和后台任务调度。已有 `config.py`、`config_schema.py`、`state.py`、`history.py`、`process_runner.py` 等模块，但页面展示与交互仍集中在 App 中。

本次按职责拆分，使页面组件可以独立理解和验证，同时保持现有 TUI 的用户行为。完成后，App 主要负责页面组合、导航、会话引擎、项目选择、任务生命周期和跨组件协调。预计 `app.py` 可降至约 1,000 至 1,400 行；行数用于观察拆分效果，不作为机械验收门槛。

### 1.1 范围

- 抽取独立样式文件和自定义控件。
- 抽取错误报告的数据读取、合并及内容反查逻辑。
- 封装配置页、项目详情页和 Zotero 面板，明确状态归属及交互接口。
- 更新受迁移影响的测试导入、mock 路径和样式断言，补充关键边界的回归测试。
- 确保样式资源随安装包分发，并保留原有 TUI 启动入口。

### 1.2 非目标

本次不改变界面布局、主题、快捷键、用户可见文案、配置结构、翻译流程、事件协议、项目元数据格式或 Zotero 业务语义。不引入新依赖，不拆分项目管理和后台任务调度，不重写已有配置、历史、状态或进程模块，也不把本次迁移扩展为对所有私有方法的长期兼容承诺。

## 2. 方案选择

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| 只迁出样式、控件和纯数据处理 | 改动小，便于先验证迁移机制 | 页面业务仍集中在 App，作为第一阶段 |
| 按页面封装组件，并抽取纯数据处理 | 页面拥有局部状态，通过明确接口与 App 通信 | 需处理事件冒泡、生命周期和 mock 路径，作为最终方案 |
| 把 App 方法搬入多个 mixin | 快速缩短单个文件 | 方法仍共享整个 App 的状态，职责和依赖没有得到改善，不采用 |

采用前两项组合的渐进路线。每个阶段都应保持应用可启动，第二阶段按组件逐一迁移，避免一次替换所有页面交互。

## 3. 模块结构与依赖

```text
src/tui/
  app.py               # 应用入口、导航、任务和项目状态协调
  app.tcss             # 从 DEFAULT_CSS 迁出的现有样式
  widgets.py           # 标题、表格、输入框和标签容器
  config_page.py       # ConfigPage：配置表单、持久化和预览
  project_detail.py    # ProjectDetail：项目产物及详情展示
  error_reports.py     # 错误报告数据读取、合并和内容反查
  zotero_panel.py      # ZoteroPanel：搜索、选择和导入交互
  config.py            # 继续负责配置读写
  config_schema.py     # 继续负责字段定义与值归一化
  state.py             # 继续负责项目、任务状态及事件应用
  history.py           # 继续负责历史与项目元数据
  input_parser.py      # 继续负责输入解析和校验
  runner.py            # 保留任务执行入口
  process_runner.py    # 继续负责翻译子进程
  zotero_adapter.py    # 继续负责 Zotero API 访问
```

依赖方向为 App 组合页面组件，页面组件使用通用控件和现有底层模块。`ProjectDetail` 组合 `ZoteroPanel` 并使用 `error_reports.py`。新增模块不得反向导入 `app.py`，也不得通过动态导入 App 或修改模块全局变量恢复旧耦合。

沿用现有 `Vertical` 等容器结构，将原有页面根容器替换为对应组件，避免额外增加影响布局的包装层。页面和控件 ID 保持不变；页面切换继续使用现有 `ContentSwitcher`。

## 4. 职责与状态归属

### 4.1 App 与通用控件

App 保留 `effective_engine`、`tasks`、`current_task`、选中项目身份、项目管理多选、任务进程和取消记录。项目身份继续由 `(task_id, project_name)` 确定，不能退化为只按项目名定位。

App 保留任务提交、终止、删除、重译、历史合并、runtime 事件应用、元数据保存及通知去重。`@work` 后台任务继续通过 `call_from_thread` 回到 UI 线程。原有 `run_tui_task` 替换检测兼容分支保留在 App，本次不改变进程通信和任务失败语义。

`widgets.py` 迁入艺术字常量及构建函数、`ResponsiveAppTitle`、三个自定义表格、入口输入框、Zotero 搜索框和两个标签容器。保持现有名称、点击防重复行为、快捷键和 resize 钩子。

第一阶段允许控件暂时沿用现有 App 回调。第二阶段中，错误表 resize 和 Zotero 搜索、选择、resize 由所属页面处理，控件发送明确消息；入口提交和项目管理仍由 App 接收。消息携带所需的行索引或操作意图，不携带整个 App。

### 4.2 ConfigPage

`ConfigPage` 拥有当前配置快照、表单加载保护标记和字体候选缓存，负责控件生成、分组、提示、profile 选择、表单填充、值收集、归一化、即时保存和 TOML 预览。配置读写继续调用 `config.py`，字段语义继续使用 `config_schema.py`。

对 App 提供以下操作边界；具体签名在 implementation plan 中按现有调用确定：

- 加载已保存配置并填充表单。
- 按当前会话引擎重建字段并填充现有配置。
- 获取完整配置快照，供 App 确定历史输出目录等操作使用。
- 配置成功保存后发出 `ConfigChanged` 消息，携带完整配置快照。

App 不保留第二份可独立修改的配置对象。若为现有调用保留 `current_config` 访问，使用转发属性读取或设置组件状态。配置页尚未加载时，配置查询保留现有按需读取已保存配置的回退行为，不能因快照为空而忽略用户的输出目录或 Zotero 设置。配置页修改默认引擎只影响未来启动；当前会话引擎继续由 App 控制。

配置控件的 `Changed` 事件在页面内处理并停止冒泡，App 只处理入口的引擎切换。异步重建由配置页管理，字段卸载、挂载、填充值及延迟事件期间持续保护持久化；普通挂载和切换会话引擎不能误写配置。合法用户编辑保存一次并更新预览；非法输入显示现有错误提示，不写入配置。

### 4.3 ProjectDetail

`ProjectDetail` 拥有详情页控件、当前展示的项目引用和关联任务日志快照。负责 TeX、源/译文 Markdown、术语 CSV、错误表和日志的展示，以及按引擎切换 tab 可见性。

App 提供项目、关联任务日志和用于 Zotero 自动匹配的上下文；组件不遍历 App 的任务列表。组件至少支持展示项目、刷新日志与术语、刷新错误表以及切换会话引擎。迁入日志合并和进度压缩函数，并保持原有输出规则。

App 先应用 runtime 事件；非日志事件继续完成原有历史、元数据、通知处理，再协调详情刷新。日志事件沿用局部刷新后返回的路径，不新增元数据保存或让每条日志触发所有产物文件重读。跨任务同名项目必须按完整项目身份路由，详情组件不能自行更改 App 的项目选择。

文件路径回退、缺失提示、读取失败提示、高亮、滚动区域和日志顺序保持现状。展示中发现产物路径后，保留现有必要的路径回填；任务状态变更仍只由 App 和 `state.py` 负责。

### 4.4 error_reports.py

该模块只依赖标准库和必要的项目状态类型，不依赖 Textual、App 或具体表格。接收明确的项目产物信息，返回报告数据和显示字段；表格构建、列宽、Rich 状态色和文字截断由详情组件负责。

迁入最终/初始报告读取、稳定键合并、状态判定、位置/类型/问题文字转换和 map 文件内容反查。保留 `(part, num_or_ph)` 合并键、新旧报告字段兼容、最终报告优先及初始报告剩余项的已解决状态；没有报告时，继续展示项目错误或 PDF 警告。

缺失、损坏、非列表 JSON 继续按现有行为处理。产物路径解析返回明确结果，由详情组件完成必要的路径回填，数据读取函数不修改 UI 或任务状态。本次不加入缓存、改变容错策略或升级报告格式。

### 4.5 ZoteroPanel

`ZoteroPanel` 拥有库列表、搜索结果和条目多选状态，负责搜索、自动匹配、结果填充、列宽调整、PDF 附件导入及 Lite Markdown 子笔记导入。Zotero 网络访问继续交给 `ZoteroAdapter`，本次保持现有执行方式，不额外引入异步网络重构。

详情组件向面板提供当前项目、完整项目身份、输入类型、自动匹配所需的 arXiv ID、会话引擎和当前 Zotero 配置。自动匹配输入仍由 App 按原有优先级提取。面板不访问 App 的任务列表或配置控件；配置保存后，App 将新的 Zotero 配置传给面板。

切换项目时清空结果和多选，保持原有行为。面板更新项目的 `zotero_status`，通过 `StatusChanged` 消息把提示交给 App 的统一通知入口。保留 adapter 工厂注入能力，测试使用假 adapter，不访问真实 Zotero 或凭据。调用结果仍按条目统计成功和失败，保留局部失败时继续处理剩余条目的语义。

PDF 导入和 Markdown 导入仍共用现有环境变量名配置，并仅在原有导入操作需要时由业务代码解析凭据。重构、文档核验和测试不得读取或输出真实密钥。

## 5. 样式、通信与兼容性

### 5.1 样式资源

将 `DEFAULT_CSS` 内容原样迁至 `src/tui/app.tcss`，由 App 的 `CSS_PATH` 加载。路径以应用 Python 模块位置为基准，不依赖启动 cwd。`setup.py` 显式将 `.tcss` 纳入 `src.tui` 的包资源，保证普通安装和 editable 安装都可用。

依赖 `LaTeXTransTuiApp.DEFAULT_CSS` 字符串的测试调整为读取资源或验证实际布局；不为旧样式断言保留第二份 CSS。迁移后的组件根容器保持原有 ID、容器布局和 CSS 匹配关系。

### 5.2 通信边界

App 向组件发送数据或调用明确的刷新方法；组件向上发送用户操作或状态消息。配置事件和 Zotero 控件事件由各自组件处理，处理后停止冒泡，App 移除对应的重复分支。禁止同一动作在组件和 App 各执行一次。

只定义跨组件实际需要的消息，不引入通用事件总线、全局服务容器或统一 controller 基类。组件自己的挂载与字段重建由自身负责；应用启动顺序应保证 App 在调用组件方法前，其所需子控件已经挂载。

### 5.3 保留入口与导出

- 保留 `src.tui.app:run`、`LaTeXTransTuiApp` 和 `PAGE_ENTRY`、`PAGE_DETAIL`、`PAGE_TASKS`、`PAGE_CONFIG`。
- 在 `app.py` 显式重新导出当前测试使用的艺术字常量、标题构建函数、自定义控件及日志辅助函数，导出绑定指向新模块中的同一对象。
- App 对外使用的操作入口可以保留薄委托方法，例如加载配置页、刷新详情、Zotero 搜索与导入；业务实现只存在于所属组件。
- 不承诺迁移前所有私有方法和模块级依赖的 monkeypatch 路径不变。测试更新为在实际查找依赖的模块上 patch；保留 App 中 runner 兼容分支所依赖的替换路径。

## 6. 迁移阶段

### 第一阶段：抽取基础模块

1. 迁出样式并补齐包资源声明，保持当前页面组合和事件路由。
2. 迁出通用控件、标题常量和函数，在 App 保留显式重新导出。
3. 抽取错误报告数据处理，App 暂时调用新模块，保持错误表展示不变。
4. 更新相关导入、样式断言和测试依赖路径，验证启动、样式加载及错误报告行为。

第一阶段完成时，不提前迁移任务状态或页面业务，不让后续组件成为当前启动的必要依赖。

### 第二阶段：逐一封装页面组件

1. 迁入 `ConfigPage`，同时迁移持久化保护和 mock 路径，移除 App 重复处理的配置事件。
2. 迁入 `ZoteroPanel`，迁移搜索结果状态和局部交互，改为向 App 发送状态提示。
3. 迁入 `ProjectDetail`，组合 Zotero 面板和产物展示，App 通过项目身份及上下文协调刷新。
4. 完成通用控件的所属组件消息路由，移除残留页面业务、重复状态和无用导入。
5. 核验入口、导出、CSS 包资源以及跨组件行为，更新 implementation plan 的完成标记及实现说明。

每个组件迁移后先完成针对该组件的验证，再迁移下一个。若尚未迁移的调用仍需要兼容委托，明确其目的并在后续步骤清理，避免长期保留两套业务实现。

## 7. 验证与验收

### 7.1 测试范围

继续使用 `unittest`。纯数据处理测试不启动 TUI；组件测试仅在需要验证生命周期、事件和布局时使用 Textual `run_test()`。复用和调整现有测试，新增测试覆盖迁移风险，不用方法数量、文件行数或每个私有方法作为测试目标。

| 边界 | 必须验证的行为 |
| --- | --- |
| 入口与导出 | 原有入口可导入，CLI 引擎优先级不变，重新导出指向同一对象 |
| 样式资源 | 资源存在于安装包，从临时 cwd 启动仍可加载；宽屏、窄屏及两种引擎布局正常 |
| 控件事件 | Enter 提交/搜索一次，表格单击只切换一次，标签快捷键的作用域不变 |
| 配置生命周期 | 初次挂载和会话切换不保存；延迟 Changed 不误写；合法编辑保存一次，非法编辑不保存 |
| 配置语义 | profile、字体候选、隐藏引擎字段及未知配置元数据保留；默认引擎不强制切换会话 |
| 错误报告 | 新旧字段、初始/最终报告合并、项目错误/PDF 警告回退、缺失/损坏文件及 map 内容反查 |
| 详情与日志 | Heavy/Lite tab 和产物正确，日志顺序及进度压缩一致，实时日志只刷新相应项目 |
| 项目身份 | 两个任务包含同名项目时，选择、完成事件和详情更新仍按 task_id 区分 |
| 表格 resize | 错误表、Zotero 表和项目表重新计算列宽，选择与游标行为不退化 |
| Zotero | 项目切换清空选择；搜索、自动匹配、PDF/Markdown 导入及部分失败统计保持现状 |
| 任务生命周期 | 新组件接入不改变提交、取消和任务事件处理，保留取消后忽略迟到完成事件的行为 |

实现时拆出与新增模块对应的简单测试文件；App 集成测试保留跨页面协调验证。迁移测试时更新依赖 patch 的实际位置，不依靠 `create=True` 掩盖错误路径。

### 7.2 配置与外部服务隔离

任何 `run_test()` 交互必须在整个生命周期内拦截真实配置写入，包括控件赋值、点击、`pilot.pause()` 和待处理事件排空。迁移到 `config_page.py` 后，保存函数的 patch 必须覆盖新的查找位置；保留旧 App mock 并不能保护新组件。

优先从临时工作目录运行测试，并使用假配置、假 adapter 和假任务进程。沿用真实 `config/ui.toml` 的哈希或 diff 核验，确认测试没有改变用户配置；不把配置内容打印到日志。测试不调用真实翻译 API 或 Zotero 服务，也不读取真实密钥。

项目运行与测试均使用本地 `latextrans` conda 环境。按项目 TUI 专项规则，默认定向运行本次新增的 TUI 回归测试；本次修改的既有用例在 implementation plan 中列出定向验证，不默认运行全部 TUI 测试。仅当用户明确要求时运行完整 TUI 套件。

打包核验需要确认 `.tcss` 出现在构建产物中，并验证安装后的资源定位。若构建会生成 `build/`、`dist/` 或元数据目录，先记录风险，使用临时输出目录并检查最终工作区。必要依赖缺失且无简单替代时，报告具体缺失项，不伪造构建结果。

### 7.3 完成条件

- 上述模块均形成明确职责，新增模块没有反向导入 App。
- App 不再实现配置表单、错误报告数据处理或 Zotero 业务，只保留必要协调和委托。
- 配置、Zotero 搜索状态和任务状态各有唯一所有者，没有两份可独立修改的副本。
- 原有入口、约定导出、控件 ID、样式、快捷键及业务行为得到保留。
- 定向验证通过，真实 UI 配置未被测试修改；未执行的验证及原因单独记录。
- 最终 diff 只含本次拆分及必要测试、包资源、计划说明，不混入用户配置和生成产物。

## 8. 风险与处理

主要风险来自容器层级改变、控件事件重复处理、异步填充触发保存、依赖迁移后 mock 失效，以及 `.tcss` 在普通安装中缺失。分别通过保留根容器结构、明确事件接收者、完整生命周期保护、更新实际依赖查找位置和安装包资源核验处理。

Textual 文档索引提供的是当前版本说明，项目声明为 `textual>=0.86.0`。实现前必须在 `latextrans` 环境确认实际版本，并核验本次使用的 API 在该版本可用；本次不以升级 Textual 作为重构前提。
